# keycloak в kubernetes

## Как это работает

keycloak используется как бастион сервис аутентификации. Через него пользователи входят в приложения и получают токены доступа.

Для развёртывания я подготовил helm чарт, который создаёт keycloak и кластер postgres через cnpg operator.

В keycloak настроен realm `app`, в котором есть два клиента `frontend` и `backend`, пользователь `fedor` и роли `user` и `admin`. Вся конфигурация realm описана в json.

Самих приложений frontend и backend в кластере нет. Это просто клиенты, которые зарегистрированы в keycloak для примера работы авторизации.

База postgres работает с основной нодой и репликой. За её состоянием следит cnpg operator. Если основной экземпляр перестанет работать, оператор может переключить работу на реплику.

Доступ к keycloak настроен через ingress. Обычные пользователи могут заходить на страницу авторизации, а доступ к админке ограничен по ip. Дополнительно настроена networkpolicy, чтобы к keycloak нельзя было подключиться напрямую из других подов.

## Что уже должно быть в кластере

В самом задании не было указано, что нужно разворачивать kubernetes, ingress controller, ceph или другие инфраструктурные компоненты.

Поэтому я сделал проект с расчётом на то, что эти компоненты уже развёрнуты в кластере.

В репозитории нет манифестов для установки ceph, csi драйвера и storageclass. Всё это настраивается отдельно, а в helm чарте указывается уже существующий storageclass.

Для локальной проверки использовал обычное локальное хранилище. Этого достаточно, чтобы проверить работу postgres, pvc и восстановление данных.

Также добавил два bash скрипта для создания бэкапа и восстановления postgres. Они позволяют сохранить базу и при необходимости восстановить её из дампа.
